# Git 协作与交付规范设计

## 目标

为本项目提供一份放在 `.codex` 目录、可被开发人员和自动化代理共同执行的 Git 协作规范。它覆盖开始工作、功能分支、与 `main` 同步、语义化解决冲突、提交、推送、合并、交付、回滚和审计记录。

## 已确认约束

- 开发在功能分支完成，交付目标为 `main`。
- 不得使用 `git rebase`，也不得用 `git pull --rebase` 替代它。
- 合并负责人在本地执行 `git merge --no-ff <feature-branch>`，验证后推送。
- 冲突必须按业务语义处理。默认保留旧功能和新功能；只有确有必要时才能删除或替换旧功能，并完整说明原因、影响、替代方案和验证结果。
- 提交命令使用 `git commit -m "本次工作内容"`；提交说明必须真实、具体地描述本次工作。
- 回滚使用新增反向提交的 `git revert`，禁止改写共享历史。

## 文档结构

最终规范位于 `.codex/GIT_COLLABORATION_AND_DELIVERY_STANDARD.md`，由九部分组成：

1. 适用范围、原则、术语和角色。
2. 分支、权限和受保护主干规则。
3. 开始工作、同步主干及拉取代码的标准命令。
4. 冲突分级、处理流程、验收和必须记录的信息。
5. 提交、推送、合并与远端一致性检查。
6. 交付说明、验证记录、文档更新和依赖/数据库变更要求。
7. 回滚、紧急修复和审计留痕。
8. 禁止操作与安全边界。
9. 可复制的检查清单和命令模板。

## 关键设计决策

文档采用“规则 + 操作步骤 + 验收证据 + 模板”的形式，而不是只给出命令。这样既能防止误用 `rebase` 和强推，也能在冲突发生时要求开发者理解双方改动的业务意图，避免用“选 ours/theirs”或删除旧代码来换取表面上的干净合并。

规范不强制使用 Pull Request 平台或固定 CI 工具，以适配当前本地合并后推送的流程；若仓库启用 PR/CI，则要求它们作为合并前的额外门禁，不替代本规范的本地验证和交付记录。

## 验收标准

- 文档中的常规流程不包含 `rebase`。
- 每个关键阶段都有可执行命令和完成判定。
- 对文本、配置、业务逻辑、删除/重构、依赖锁文件和二进制冲突分别规定处理方式。
- 明确禁止为新增功能无正当理由删除旧功能。
- 明确规定只暂存本任务文件、冲突标记扫描、差异检查、测试记录和安全回滚。
