# Git 协作与交付规范

> **适用范围：** 本仓库所有代码、配置、脚本、文档和自动化变更。
>
> **强制原则：** 不使用 `git rebase`；不改写共享历史；冲突按业务语义解决；新增功能不得无正当理由破坏或删除既有功能。
> **最终解释：** 当本规范与任务要求冲突时，以经项目负责人确认的任务要求为准，并在交付记录中说明例外。

---

## 1. 目标、术语与基本原则

### 1.1 目标

通过可追溯、可验证、可回滚的流程，把功能分支上的工作安全合入 `main`。流程的重点不是“尽快消除冲突”，而是确保合并后完整保留应有的业务行为。

### 1.2 术语

| 术语 | 含义 |
| --- | --- |
| `main` | 受保护的集成主干，只存放可验证、可交付的代码。 |
| 功能分支 | 从最新 `main` 创建、用于一个明确任务的短生命周期分支。 |
| 合并负责人 | 负责审查交付物、解决跨分支语义冲突、执行本地非快进合并并推送 `main` 的人员。 |
| 语义冲突 | 两段代码即使能自动合并，也可能改变、覆盖或遗漏业务行为的冲突。 |
| 交付记录 | 本次目标、文件、验证、限制、冲突决策和提交号的书面说明。 |

### 1.3 不可违反的原则

1. **主干可用。** 不直接在 `main` 开发；只有完成验证的功能分支可合入。
2. **历史真实。** 禁止改写已共享的提交历史；合并使用显式 merge commit。
3. **行为优先。** 解决冲突时先理解双方意图，再编辑代码；不能为让 Git 通过而牺牲任一方已有功能。
4. **最小范围。** 每个提交和每次合并只包含本任务所需文件，不夹带格式化、依赖升级或其他人的未完成工作。
5. **先验证后交付。** 代码、配置和文档都需要与变更风险相称的验证证据。
6. **可审计、可回滚。** 每次交付都能定位到分支、提交、验证结果和恢复办法。

## 2. 角色、权限与分支规则

### 2.1 角色职责

| 角色 | 可以做什么 | 必须承担什么责任 |
| --- | --- | --- |
| 开发者 | 创建并推送功能分支，处理自己分支与 `main` 的冲突 | 自测、最小化暂存范围、提交真实说明、提供交付记录。 |
| 审查者 | 审查差异、测试和冲突处理记录 | 关注旧行为是否被覆盖、删除是否合理、验证是否足够。 |
| 合并负责人 | 在本地将功能分支非快进合入 `main` 并推送 | 确认分支已同步、执行合并前后验证、保留冲突决策和发布证据。 |
| 紧急修复负责人 | 在 `hotfix/` 分支处理生产级问题 | 缩小变更范围，完成回归验证，并补齐事后记录。 |

同一人可以兼任多个角色，但不得跳过相应检查。

### 2.2 分支命名

使用小写字母、数字和短横线，名称必须能说明目的：

```text
feature/<任务号>-<主题>   # 例如 feature/128-vnpy-minute-backtest
fix/<任务号>-<主题>       # 例如 fix/217-minute-volume-unit
docs/<任务号>-<主题>      # 例如 docs/031-git-standard
hotfix/<任务号>-<主题>    # 例如 hotfix/301-order-rounding
```

一个分支只解决一个可描述的任务。发现任务同时包含无关重构、依赖升级和功能开发时，应拆分为独立分支和独立提交。

### 2.3 `main` 规则

- `main` 不用于日常编码、调试或临时提交。
- 合并负责人只能在本地完成以下形式的合并：

  ```powershell
  git merge --no-ff <feature-branch>
  ```

- 合并前后都必须验证；验证失败则停止推送，保留现场并修复问题。
- `main` 被他人更新时，先同步远端再继续，不能以覆盖远端的方式推送。

## 3. 开始工作与拉取代码

### 3.1 开始前检查

每次开始任务前，在仓库根目录执行：

```powershell
git status --short
git fetch origin --prune
git branch --show-current
```

完成判定：

- 明确知道当前分支和所有未提交文件的来源。
- 当前工作区若有其他人的改动、来源不明的文件或与本任务无关的改动，**不得删除、覆盖、暂存或提交**。
- 自己尚未完成的工作应先提交到自己的分支；确需暂时收起时可使用具名 stash，并在本次任务结束前恢复和核对：

  ```powershell
  git stash push -u -m "wip: <任务号>-<简要说明>"
  git stash list
  ```

  `stash` 只是本地临时保存，不能代替提交或交付。

### 3.2 从最新主干创建功能分支

```powershell
git switch main
git status --short
git fetch origin --prune
git merge --ff-only origin/main
git switch -c feature/<任务号>-<主题>
```

`git merge --ff-only origin/main` 失败时，说明本地 `main` 不应继续使用。不要用 rebase、强推或硬重置“修好”它；先检查差异并由合并负责人处理。

### 3.3 功能分支工作期间同步 `main`

功能分支开发时间超过一个工作日、开始解决较大冲突前、或准备交付前，都必须同步一次远端主干：

```powershell
git switch feature/<任务号>-<主题>
git status --short
git fetch origin --prune
git merge origin/main
```

这是本项目唯一允许的主干同步方式。若没有冲突，继续测试；若有冲突，严格执行第 4 节。

### 3.4 禁止的拉取方式

以下命令或等价操作一律禁止：

```powershell
git rebase ...
git pull --rebase
git config pull.rebase true
git push --force
git push --force-with-lease
git reset --hard ...
```

普通 `git pull` 不作为团队标准命令，因为它隐藏了 fetch 与 merge 两个步骤。统一显式执行 `git fetch origin --prune` 和 `git merge ...`，使同步点和冲突来源可见、可审计。

## 4. 冲突处理：以业务语义为准

### 4.1 总规则

冲突不是“选当前版本”或“选远端版本”的文本题。处理目标是：**双方本来正确的业务意图都得到保留，除非经过论证确认不能共存。**

不得为了合并方便而：

- 删除旧接口、旧字段、旧策略、旧页面、旧校验或旧测试；
- 用整文件的 `ours`/`theirs` 覆盖另一方改动；
- 仅凭“测试能跑”认定冲突解决正确；
- 把冲突标记、调试代码、临时绕过逻辑带入提交。

### 4.2 标准处理流程

1. **固定现场并识别文件。**

   ```powershell
   git status
   git diff --name-only --diff-filter=U
   git diff
   ```

2. **逐文件写明双方意图。** 先在交付记录或合并说明中列出：
   - 功能分支新增/修改了什么行为，服务什么场景；
   - `main` 新增/修改了什么行为，服务什么场景；
   - 最终方案如何保留两边行为，或为什么必须替换其中一边；
   - 需要补充的测试和兼容/迁移措施。

3. **按类型选择处理方法。** 参见第 4.3 节；编辑后不得保留冲突标记。

4. **验证冲突结果。** 至少执行：

   ```powershell
   rg -n '^(<<<<<<<|=======|>>>>>>>)' .
   git diff --check
   git diff
   ```

   第一条命令无输出才算通过；`git diff --check` 无输出才算通过。之后运行本任务测试，以及受影响旧功能与新功能的回归测试。

5. **完成合并。**

   ```powershell
   git add <已核对的文件>
   git diff --cached --check
   git diff --cached
   git merge --continue
   ```

   如果确认本次合并不应继续，使用 `git merge --abort` 回到合并前状态；不要用 `reset --hard` 清场。

### 4.3 冲突分类与处理要求

| 类型 | 正确做法 | 必须验证 |
| --- | --- | --- |
| 文本、注释、格式 | 保留两边仍有意义的内容；统一术语和格式。 | 构建/静态检查；确认没有遗漏实际代码。 |
| API、模型、配置字段 | 默认采用向后兼容的“新增字段 + 合理默认值”；不要静默改名或删除旧字段。 | 旧调用与新调用都可用；配置示例和校验同步更新。 |
| 业务逻辑、策略、交易规则 | 明确输入、条件、优先级和输出；通过组合、分支或显式迁移保留双方规则。 | 分别覆盖旧场景、新场景和两规则同时触发的边界场景。 |
| 删除或重构 | 先证明旧实现无法安全共存，再定义替代实现、迁移窗口、兼容层和回滚路径。 | 替代功能、依赖方、数据迁移和回滚均验证。 |
| 依赖清单与锁文件 | 先合并源清单（如 `pyproject.toml`、`package.json`），再用受控工具重新生成锁文件。 | 安装/解析成功；测试通过；无无关依赖漂移。 |
| 文档、接口说明 | 保留两方对外承诺，若行为变更则明确版本、迁移方式和弃用时间。 | 示例命令或示例请求可执行。 |
| 二进制、图片、生成文件 | 优先保留两个命名清晰的资源或从源文件重新生成；不能靠 Git 标记猜测。 | 引用路径有效、构建产物正常、版本/来源可追溯。 |

### 4.4 删除或替换旧功能的例外门槛

只有同时满足以下条件，才可以删除、替换或改变旧功能的对外行为：

1. 说明旧行为与新要求、正确性、安全性、维护成本或平台限制之间的具体冲突；
2. 说明为什么“双轨保留”“兼容层”“配置开关”或分阶段迁移不可行；
3. 给出替代能力、受影响调用方、数据/配置迁移步骤和回滚办法；
4. 获得任务负责人或合并负责人的明确确认；
5. 在交付记录中写明理由、影响范围和验证结果。

“代码看起来重复”“文件冲突太复杂”“新功能更先进”都不是删除既有功能的充分理由。

### 4.5 整文件选边的限制

`git checkout --ours <file>`、`git checkout --theirs <file>` 或类似整文件选边，只能用于可再生文件、纯格式文件或已经逐项比对确认的二进制文件。使用时必须记录：文件名、选择原因、被舍弃内容是否已在其他文件保留、以及验证结果。对业务代码、配置、接口定义和测试代码，默认禁止整文件选边。

## 5. 编码、暂存与提交

### 5.1 工作要求

- 改动前先阅读相关代码、测试、配置和调用点；不要凭文件名猜测行为。
- 新功能至少验证自身路径；修改旧逻辑必须回归旧路径。
- 不顺手重排无关代码、全局格式化、升级无关依赖或清理他人文件。
- 不提交密钥、令牌、账户信息、私有数据、日志、缓存、构建产物或本地环境文件。

### 5.2 暂存前检查

仅逐文件暂存本任务内容，禁止习惯性使用 `git add .` 或 `git add -A`：

```powershell
git status --short
git add backend/app/example.py backend/tests/test_example.py docs/example.md
git diff --cached --check
git diff --cached
```

完成判定：

- 暂存差异只包含本任务文件；
- 无空白错误、冲突标记、调试输出、未解释的删除或密钥；
- 每一处删除和重要行为变化都能在需求或交付记录中找到依据。

### 5.3 提交规范

一个提交只表达一个可审查、可回滚的工作单元。提交信息必须使用实际工作内容，禁止提交 `update`、`fix`、`test`、`wip`、`改一下` 等无意义文字。

```powershell
git commit -m "本次工作内容"
```

其中“本次工作内容”必须替换为真实说明。推荐格式：

```powershell
git commit -m "feat(backtest): 接入 VNPy 分钟回测撮合"
git commit -m "fix(strategy): 按手转换分钟成交量"
git commit -m "docs(git): 新增协作与交付规范"
```

可用类型为 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。复杂改动应在提交正文或交付记录中补充：变更内容、验证命令及结果、已知限制、兼容/迁移说明。

提交后检查：

```powershell
git show --stat --oneline HEAD
git status --short
```

### 5.4 已推送提交的修正

已推送的提交不得通过 rebase、`commit --amend` 后强推或历史重写修正。应新增一个说明明确的修复提交；若要撤销，执行第 8 节的 `git revert` 流程。

## 6. 功能分支推送与交付

### 6.1 推送前门禁

在功能分支同步 `origin/main` 并解决所有冲突后，执行：

```powershell
git status --short
git diff origin/main...HEAD --check
git log --oneline origin/main..HEAD
```

然后运行与改动匹配的检查，例如单元测试、集成测试、静态检查、构建、接口验证或手工验收。不要把“命令未执行”写成“通过”。

### 6.2 推送功能分支

```powershell
git push -u origin feature/<任务号>-<主题>
git status -sb
```

若推送被拒绝，先执行 `git fetch origin --prune`，检查远端新增提交，并用 merge 同步；不得强推覆盖远端。

### 6.3 必交付记录

交付给审查者或合并负责人时，至少提供以下内容：

```markdown
## 交付记录

- 任务/目标：
- 分支：
- 提交：
- 改动文件与作用：
- 保留的旧行为：
- 新增或变更的行为：
- 已执行验证（命令、结果）：
- 未执行验证及原因：
- 已知限制、风险与回滚方式：
- 冲突记录（无则写“无”）：
  - 冲突文件：
  - 双方意图：
  - 最终保留行为：
  - 删除/替换理由及确认人（如适用）：
  - 验证结果：
```

涉及数据库、数据格式、接口、配置、依赖或部署步骤时，交付记录必须额外说明兼容性、升级/回退命令和影响对象。

## 7. 合并到 `main` 的流程

### 7.1 合并前核验

合并负责人应确认功能分支提交号、交付记录和验证证据对应同一版本。然后执行：

```powershell
git fetch origin --prune
git switch feature/<任务号>-<主题>
git merge --ff-only origin/feature/<任务号>-<主题>
git switch main
git status --short
git merge --ff-only origin/main
git rev-list --left-right --count main...origin/main
```

最后一条命令应输出 `0 0`。若不是，停止合并并先找出本地与远端主干的差异来源；不得用覆盖式推送处理。

### 7.2 执行非快进合并

在确认 `main` 已同步、工作区干净且测试基线正常后，执行：

```powershell
git merge --no-ff feature/<任务号>-<主题>
```

若出现冲突，按第 4 节处理。合并提交信息应说明被合并的任务和主要目标，必要时在正文中记录冲突决策。

### 7.3 合并后验证与推送

合并完成但尚未推送时，必须在 `main` 上重新执行：

```powershell
git status --short
git log --graph --decorate --oneline -10
git diff HEAD^1..HEAD --check
```

再运行合并前承诺的测试/构建/验收。通过后才可推送：

```powershell
git push origin main
git fetch origin --prune
git rev-list --left-right --count main...origin/main
git log -1 --oneline origin/main
```

完成判定：`git rev-list --left-right --count main...origin/main` 输出 `0 0`，且远端 `main` 的最新提交为本次合并提交。

### 7.4 合并后收尾

- 更新交付记录，补上最终 merge commit、实际验证结果和发布日期/时间。
- 功能分支在确认远端主干已包含该 merge commit 后再删除；保留任务、提交和交付记录的关联。
- 如果需要删除远端功能分支，先取得负责人确认，再执行删除；分支删除不等于删除审计记录。

## 8. 回滚、紧急修复与故障处理

### 8.1 常规回滚

共享分支发生错误时，优先新建反向提交，禁止重写历史：

```powershell
git switch main
git fetch origin --prune
git merge --ff-only origin/main
git revert <需要撤销的提交SHA>
```

撤销一个 merge commit 时，保留 `main` 作为主线：

```powershell
git revert -m 1 <merge-commit-SHA>
```

回滚提交同样必须经过测试、交付记录和正常推送流程。回滚后还需说明：触发原因、受影响范围、临时缓解、后续修复分支和是否需要数据修复。

### 8.2 紧急修复

紧急问题使用 `hotfix/<任务号>-<主题>` 分支，流程仍为：从最新 `main` 创建分支 → 最小修复 → 回归验证 → 推送 → 本地 `git merge --no-ff` 合并。紧急性不能成为跳过验证、强推、rebase 或直接改写主干的理由。

### 8.3 无法安全解决的冲突

出现下列任一情形时，停止自动合并，保留冲突现场并升级处理：

- 无法确定任一改动的业务意图或责任人；
- 两个变更对同一用户场景给出互斥规则；
- 涉及数据丢失、资金计算、权限、安全或对外兼容性；
- 为解决冲突必须删除旧功能，但尚未满足第 4.4 节；
- 测试不能覆盖受影响的关键路径。

升级记录必须写明冲突文件、候选方案、风险、需要确认的业务决策和阻塞时间。未获得决策前，不推送到 `main`。

## 9. 安全、审计与禁止操作

### 9.1 禁止操作清单

| 禁止操作 | 原因 | 正确替代 |
| --- | --- | --- |
| `git rebase` / `git pull --rebase` | 改写或重排历史，增加共享分支追踪和冲突风险。 | `git fetch origin --prune` 后 `git merge origin/main`。 |
| `git push --force` / `--force-with-lease` | 可能覆盖他人提交和审计记录。 | 合并远端新增提交，或联系合并负责人。 |
| `git reset --hard` | 可能丢失本地未提交工作。 | `git merge --abort`、具名 stash、或新建修复提交。 |
| `git add .` / `git add -A` | 容易混入无关文件、密钥、数据和他人改动。 | 显式列出要暂存的文件。 |
| 业务文件整文件选 `ours` / `theirs` | 容易无声删除另一方的有效功能。 | 逐段理解、合并行为并补测试。 |
| 把 `.env`、令牌、私有数据、日志或构建产物提交 | 造成安全、合规和仓库膨胀风险。 | 使用 `.env.example`、安全配置系统和 `.gitignore`。 |

### 9.2 审计最低要求

每一次合入 `main` 的变更都应能回答：谁提交、为什么改、影响哪些文件和功能、执行了什么验证、出现什么冲突、如何解决、发生问题如何回滚。答案应在提交、交付记录、合并说明或关联任务中可找到。

## 11. 日常命令速查

```powershell
# 获取远端状态（不修改当前分支）
git fetch origin --prune

# 在功能分支同步主干（本项目标准做法）
git merge origin/main

# 查看未解决冲突文件
git diff --name-only --diff-filter=U

# 扫描冲突标记与空白错误
rg -n '^(<<<<<<<|=======|>>>>>>>)' .
git diff --check

# 精确暂存与检查
git add <文件1> <文件2>
git diff --cached --check
git diff --cached

# 本地非快进合并功能分支
git merge --no-ff feature/<任务号>-<主题>

# 安全撤销已共享提交
git revert <提交SHA>
```

本规范的任何例外均须在交付记录中明确写出“例外内容、原因、确认人、风险和补救措施”。没有记录的例外视为未获批准。
